## R1. Runtime: which Copilot Studio harness and agent shape

- **Decision**: An MCS2 CLI-authored agent (`pac copilot init --authoring-mode cli-copilot`,
  template `cliagent-*`), which runs on the **Microsoft Copilot harness** (agentic loop).
- **Rationale**: The constitution requires modern generative orchestration. This harness supports
  skills (including packages with scripts and supporting files), natively creates PDF files, and
  runs each task in a sandbox. It is the shape the mcs-assistant plugin authors.
- **Alternatives considered**: Standard harness with topics, Power Fx and Adaptive Card nodes —
  gives deterministic flows and interactive cards, but violates Principle IV (classic topics) and
  is not what the plugin's CLI authoring produces. Customer Conversation harness — aimed at
  website/voice customer service with escalation; not needed for v1.

## R2. No topics, no variables, no Power Fx: how to hold plan state

- **Decision**: Keep the trip plan as a compact **plan state JSON** that a skill script returns
  after every change. The agent passes the latest plan state back to the script on the next call.
  The script is stateless and recalculates everything from the catalog each time.
- **Rationale**: The agentic loop has no global/topic variables or Power Fx (architect guidance
  §5). Recomputing from catalog IDs on every call makes totals exact and makes it impossible for
  stale or model-edited prices to survive (Principle II, FR-013/FR-014/FR-023).
- **Alternatives considered**: Asking the model to remember and add up prices — not
  deterministic, fails SC-002. Dataverse table for plan state — adds storage, a connector and
  privacy scope for no v1 benefit (spec says drafts are not kept).

## R3. Exact pricing and validation

- **Decision**: A Python script bundled in the catalog skill (`scripts/trip_plan.py`) does all
  validation and arithmetic with `decimal.Decimal`, rounding half-up to 2 decimals, in AZN.
  Dates are evaluated in Baku time (UTC+4, no DST).
- **Rationale**: Architect decision tree: "manipulate data or execute logic in a complex way →
  skill with an embedded python file". Decimal arithmetic guarantees SC-002.
- **Alternatives considered**: A Power Automate agent flow as a pricing tool — deterministic but
  needs a flow, a connection and per-call latency; a separate AI prompt with code interpreter —
  non-deterministic code generation per call.

## R4. Catalog: knowledge source vs. skill resource

- **Decision**: Hotels and activities live in a **JSON catalog bundled with the catalog skill**
  (`references/catalog.json`), read only by `trip_plan.py`. Not a knowledge source.
- **Rationale**: The agent doesn't *search* the catalog; it must list exact items and prices.
  Architect guidance: use knowledge for semantic search; use a skill + file when the data is a
  source of truth for a procedure. RAG over prices risks paraphrased or wrong numbers.
- **Content decision**: 5 sample hotels with **fictional names** in real Baku neighborhoods, and
  6 real activity types (Old City walking tour, Gobustan & mud volcanoes, Ateshgah & Yanar Dag,
  Boulevard boat ride, Heydar Aliyev Center visit, cooking class) with indicative **sample
  prices** in AZN. Fictional hotel names avoid implying real prices for real businesses.
- **Alternatives considered**: Uploaded Excel/CSV knowledge file — searchable but not reliable for
  exact listing; Dataverse/SharePoint list + tool — right for live data later, overkill now
  (Principle VI).

## R5. Showing options with photos (cards)

- **Decision**: Render hotel options, activity options and the plan as **Markdown** generated by
  the script (heading, image, description, price line) and shown verbatim by the agent. Photos
  are referenced by public HTTPS URL.
- **Rationale**: Adaptive Cards in Copilot Studio are documented for the standard harness (topic
  nodes); there is no documented way for a CLI agent skill to emit an Adaptive Card. Markdown with
  images is what the agentic loop can produce.
- **Risk / spike**: Image rendering differs by channel (test chat vs. Teams vs. Microsoft Copilot,
  where some media types are filtered). Task T-spike verifies rendering in the Copilot Studio test
  chat first. Fallback: show a "View photo" link per item instead of an inline image.
- **Alternatives considered**: Adaptive Cards via a Power Automate flow or topic — reintroduces
  standard-harness constructs; deferred to a later feature if channels require it.

## R6. Stock photos: source and license

- **Decision**: Use freely licensed photos of Baku landmarks and neighborhoods from **Wikimedia
  Commons** (CC BY / CC BY-SA / public domain), recording URL, author and license per item in the
  catalog. Every URL is checked for HTTP 200 during implementation.
- **Rationale**: The spec allows stock photos; Commons provides stable direct URLs and clear
  licenses, and attribution can be shown in the PDF footer.
- **Alternatives considered**: Unsplash (good quality, but URLs must be curated by hand and the
  license forbids building a competing photo service — fine, but Commons is more traceable);
  placeholder services (no real Baku content).

## R7. PDF export

- **Decision**: A separate skill (`export-trip-plan-pdf`) runs `scripts/make_pdf.py`, which uses
  **reportlab** to build the PDF from the confirmed plan state. Photos are **bundled in the skill
  package** (`assets/photos/`, resized JPEGs) because the sandbox has restricted external network
  access. The harness surfaces the generated file as a download link.
- **Rationale**: The Microsoft Copilot harness natively creates PDF files and ships `reportlab`;
  generated files are offered for download in the response. Bundled photos avoid network calls.
- **Risks**: (a) Generated files are available only during the session — acceptable, the spec
  says plans aren't kept. (b) File downloads are a known gap in some channels (custom engine
  agents in Microsoft 365 Copilot); the test chat and Teams support them. (c) Whether image files
  are accepted in uploaded skill packages is not documented — the spike verifies it; fallback is
  embedding photos as base64 inside a `.py`/`.json` resource.
- **Alternatives considered**: Power Automate flow (HTML → OneDrive → convert to PDF) — needs
  OneDrive connection, stores the holder's data in a file share (privacy scope), slower.

## R8. Skill architecture

- **Decision**: Three focused, uploaded (bundle) skills plus global instructions:

  | Component | Responsibility | Why this component |
  |---|---|---|
  | Instructions (`settings.mcs.yml`) | Role, flow order (trip details → hotel → activities loop → confirmation → final plan → PDF), privacy, "confirming is not booking", AZN, always use scripts for prices, never invent | Global behavior that applies to every conversation |
  | Skill `baku-trip-catalog` | Collect/validate trip details; list hotels/activities; add/replace/remove items; recalculate and render the plan | Reusable procedure + deterministic script + catalog |
  | Skill `confirm-trip-plan` | Collect and validate holder details; show summary; require explicit confirmation; issue reference | Distinct procedure with privacy and confirmation rules |
  | Skill `export-trip-plan-pdf` | Build the final plan PDF from a confirmed plan state | Distinct file-generation procedure with its own assets |
  | Knowledge (2 public websites) | Grounded answers to off-topic practical questions (e-visa, tourism info) | Searchable factual sources (Principle II) |

- **Rationale**: Architect heuristics: few focused skills, each a real procedure; global flow
  rules in instructions (the flow happens in every conversation, so it isn't a skill). Splitting
  pricing from confirmation and PDF keeps each skill's description precise for the orchestrator.
- **Variant**: Upload variant (bundles), because skills carry scripts and assets. Sources are kept
  in `skills-src/` and imported with the plugin's `add-skill` skill (`scripts/add-skill.js`),
  which generates the anchor and sidecar YAML. The plugin notes that inline vs upload runtime
  equivalence is not yet documented; we only use upload.
- **Shared code**: each package must be self-contained, so the catalog and the pricing module
  have one source in `skills-src/_shared/` and are copied into each skill by
  `tools/sync_shared.py`; a test checks the copies match.
- **Alternatives considered**: One "travel-agent" mega-skill (rejected: sprawling, weak
  selection signal); one skill per step incl. a hotel skill and an activity skill (rejected: they
  share the same catalog and script; splitting duplicates assets).

## R9. Knowledge sources for off-topic questions

- **Decision**: Two `WebsiteKnowledgeSource` entries: the official Azerbaijan e-visa portal
  (`https://evisa.gov.az`) and the official tourism board site (`https://azerbaijan.travel`).
  Both URLs are root domains (≤2 path segments). Availability and Bing indexing are checked
  during implementation; a source that fails is dropped and listed as a gap.
- **Rationale**: Edge case "off-topic travel questions" and Principle II require grounded answers
  or a pointer to the official source.
- **Alternatives considered**: No knowledge (agent always redirects) — acceptable fallback if the
  sites can't be added.
- **Found in T044**: besides the two knowledge sources, the Microsoft Copilot harness gives the agent
  a built-in **web_search** tool, which it used for visa questions. Answers cited the official
  e-visa portal in all runs, but web search is not limited to official sites. Mitigation: the
  instructions require preferring official government and tourism sources and naming the source.
  Whether web search can be disabled for a CLI agent is undocumented — check in a later feature.

## R10. Testing approach

- **Decision**:
  1. **Script unit tests** run locally with `pytest` (Python 3.13 locally; scripts target
     Python ≥3.10 stdlib + reportlab).
  2. **Conversation tests** (spec example conversations + constitution negative tests) run against
     the pushed draft agent in the Copilot Studio test chat (browser). The plugin's
     `/mcs-assistant:chat` command was ruled out during implementation: it only reaches a
     published agent and needs an Entra app registration; results are recorded
     in `specs/001-baku-trip-planner/test-results/`.
- **Rationale**: Principle V; unit tests prove SC-002 independently of the model.

## R11. Identity and ALM values

- **Decision**: Display name `Baku Travel Planner` (19 chars); environment the demo environment
  (`https://<your-org>.crm.dynamics.com/`); project directory `agent/` at the repo root;
  publisher prefix `catmgr` (plugin default) unless the user supplies another before init;
  schema name derived by PAC. ALM: `pac copilot init` → `pull` → author → `push` → `pull`;
  `publish` only after the review gate, via the plugin's `publish-agent` skill.
- **Note**: `pac copilot init` refuses a non-empty destination, so `agent/` must not exist before
  init.
- **Found in T007**: `pac copilot init` also **published** the initial scaffold (status
  "Published"). Recorded as a constitution exception in plan.md Complexity Tracking; the reviewed
  publish in T049 replaces it.

## Spike results (T012, 2026-11-13)

Run in the Copilot Studio test chat (Preview tab, unpublished draft) with the `spike-check`
skill package (SKILL.md + `scripts/spike.py` + `assets/test.jpg`):

| Check | Result | Notes |
|---|---|---|
| 1. Bundled script runs | ✅ Pass | Sandbox: Python 3.12.16, Linux, `reportlab` 5.0.1 available |
| 2. Bundled image readable | ✅ Pass | `assets/test.jpg` listed and readable from `scripts/../assets/` |
| 3. Markdown image renders | ✅ Pass | Inline image rendered in the test chat (Wikimedia Commons HTTPS URL) |
| 4. PDF download offered | ✅ Pass | `spike.pdf` (93 KB) shown as a downloadable attachment |

**No fallbacks needed**: R5 (Markdown images) and R7 (bundled photos, reportlab PDF) stand as
designed; `--photo-style link` stays available but defaults to `inline`.

**Findings that change implementation details:**

- The skill folder is **read-only** at runtime; the first run failed writing `spike.pdf` to the
  script's working directory and the agent retried from `/app/workspace`. → `make_pdf.py` must
  write to a writable folder: `--out` if given, else the current directory if writable, else
  `/app/workspace`, else the system temp folder; it prints the full path it wrote.
- The agent wrapped the script output in a code block when told to show it "exactly as printed",
  so the image line did not render there (it rendered when the agent re-emitted it as Markdown).
  → Skills must say "show the `markdown` field as normal Markdown (not in a code block)".
- One spike conversation used ~14.6 Copilot Credits (shown in the test chat header).
- `pac copilot init` **published** the initial scaffold (status badge "Published"), as the plugin
  warned it might. Later pushes stay draft-only until T049.
- Conversation tests use the Preview tab; `/mcs-assistant:chat` needs a published agent and an
  Entra app registration and is not used before T049.
- **Removing a skill**: deleting `agent/behaviors/<skill>/` locally and pushing does **not** delete
  it in the cloud — the pre-push pull restores it. Remove skills in Copilot Studio (Build →
  Skills → remove), then `pac copilot pull`. (T013)
- **Updating an imported skill** (found in T026): `add-skill --force` re-import mints new schema
  names for the anchor/sidecars, and the next `pac copilot pull` reverts the payload files to the
  cloud copy (while reporting "0 change(s) applied"). A pull also overwrites local payload edits.
  → Update payload with `tools/stage_skill.py` **after** the pre-push pull, then validate and push.
- **Publishing (T049)**: PAC 2.15.1 `copilot publish` started the job but crashed while
  polling status (`Invalid response format`). The publish completed (portal: "Last published
  6:54 PM"). If this recurs, check the portal instead of re-running publish.
